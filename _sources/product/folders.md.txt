# Your folder

monsterbrain works on any folder of files. It reads the folder as it is and
imposes no structure ({need}`DEC_STRUCTURE_UNCHANGED`). Nothing is imported
and nothing is stored besides the last opened folder and the settings – the
files and Git are the truth.

## What monsterbrain reads

| What | Used for |
|---|---|
| Frontmatter (YAML at the top of a Markdown file) | the right panel: `summary`, `status`, `updated`, `tags`, `owner` |
| Links between files | links and backlinks in the right panel, broken links as warnings |
| Git | changed files in the tree and the change view, diffs, the date of the last change |
| Concept folders | the concepts view (below) |
| Backlog items | the backlog view (below) |

Hidden files and installed dependencies (`node_modules` and the like) are
never shown.

## Conventions it understands

monsterbrain grew out of a knowledge folder with a few conventions. They are
optional – without them the matching features simply stay empty.

- **Frontmatter with a `summary`** – a Markdown file without one gets a
  warning. Folders for unchanged third-party material (`40_sources/`,
  `50_assets/`) are not expected to have frontmatter.
- **`updated`** – a date older than the last change in Git gets a warning.
- **`[CHECK]` markers** – open questions in a text are counted as warnings
  (replaced by deciwa questions once the deciwa extension is installed).
- **Concepts** – open concepts in `<area>/10_concepts/<date>_<name>/concept.md`,
  closed ones in `<area>/90_archive/concepts/`. Their frontmatter lists in
  `results:` the files the concept produced; the concepts view shows them.
- **Facts** – verified knowledge in `<area>/20_facts/`, one Markdown file per
  topic, `_index.md` per folder as its index. The facts view lists these
  files; an extension adds their single facts.
- **Backlog** – larger future tasks and open questions in
  `<area>/05_backlog/`, one Markdown file per item (`<project>_<topic>.md`),
  `_index.md` as its index. The frontmatter says what an item is (`kind`:
  `task` or `question`), its `project` and `status` (`open`, `concept`,
  `done`, `discarded`), where it came from (`origin`) and the concept started
  from it (`concept`). Done and discarded items move to
  `<area>/90_archive/backlog/`. The backlog view lists them.

## Your folder and code repositories

A knowledge folder usually spans all projects – it stands for a whole
entity, not for one piece of software: you, a team, a company or anything
else with a knowledge graph of its own. It holds the metadata and ideas of
every project: what it is for, who is involved, what was decided and
delivered. Tools and software that come out of the work are outputs with a
repository of their own next to the folder.

| In the knowledge folder | In the repository |
|---|---|
| metadata and ideas of every project | the tool itself: code, build, tests |
| rules and ideas that hold across projects | rules of its own that only concern this tool |
| concepts – the plan for a change, also for a tool | requirements, specs and the like for this tool |
| targets for a tool: what it should do and how it is built | the actual implementation |

**The folder holds what spans projects.** Rules that hold for every project –
naming, how a concept runs, how outputs are built – are written once in the
folder. A repository can still have rules of its own and with them its own
requirements, specs and the like, when they only concern this one tool. A
concept that gets implemented creates or changes these elements in the
matching repository as well and lists the repository under `results:`.

**The repository holds what is built.** The folder can set targets and rules
for a tool and how it is built; the repository holds the actual
implementation. It may deviate on purpose – a decision made while building –
or show an older state, because the folder already describes the next step.
The folder says what is intended, the repository what exists.
