Dein Ordner¶

monsterbrain arbeitet mit jedem Ordner voller Dateien. Es liest den Ordner, wie er ist, und gibt keine Struktur vor (Die Ordnerstruktur bleibt u... (DEC_STRUCTURE_UNCHANGED)). Nichts wird importiert, und außer dem zuletzt geöffneten Ordner und den Einstellungen wird nichts gespeichert – die Dateien und Git sind die Wahrheit.

Konventionen, die es versteht¶

monsterbrain ist aus einem Wissensordner mit ein paar Konventionen entstanden. Sie sind optional – ohne sie bleiben die passenden Features einfach leer.

  • Frontmatter mit summary – eine Markdown-Datei ohne bekommt eine Warnung. Von Ordnern für unverändertes Material Dritter (40_sources/, 50_assets/) wird kein Frontmatter erwartet.

  • updated – ein Datum, das älter ist als die letzte Änderung in Git, bekommt eine Warnung.

  • [CHECK]-Marker – offene Fragen in einem Text zählen als Warnungen (ersetzt durch deciwa-Fragen, sobald die deciwa-Erweiterung installiert ist).

  • Konzepte – offene Konzepte in <area>/10_concepts/<date>_<name>/concept.md, abgeschlossene in <area>/90_archive/concepts/. Ihr Frontmatter führt unter results: die Dateien auf, die das Konzept erzeugt hat; die Konzeptansicht zeigt sie.

  • Fakten – geprüftes Wissen in <area>/20_facts/, eine Markdown-Datei pro Thema, _index.md je Ordner als Verzeichnis. Die Fakten-Ansicht listet diese Dateien; eine Erweiterung ergänzt ihre einzelnen Fakten.

  • Backlog – größere künftige Aufgaben und offene Fragen in <area>/05_backlog/, eine Markdown-Datei pro Eintrag (<project>_<topic>.md), _index.md als Verzeichnis. Das Frontmatter sagt, was ein Eintrag ist (kind: task oder question), sein project und seinen status (open, concept, done, discarded), woher er kommt (origin) und welches Konzept aus ihm entstanden ist (concept). Erledigte und verworfene Einträge wandern nach <area>/90_archive/backlog/. Die Backlog-Ansicht listet sie

Dein Ordner und Code-Repositories¶

Ein Wissensordner umfasst in der Regel alle Projekte – er steht für eine ganze Einheit, nicht für eine einzelne Software: dich, ein Team, eine Firma oder alles andere mit einem eigenen Knowledge Graph. Er enthält die Metadaten und Ideen jedes Projekts: wofür es da ist, wer beteiligt ist, was entschieden und geliefert wurde. Tools und Software, die aus der Arbeit entstehen, sind Ergebnisse mit einem eigenen Repository neben dem Ordner.

Im Wissensordner

Im Repository

Metadaten und Ideen jedes Projekts

das Tool selbst: Code, Build, Tests

Regeln und Ideen, die projektübergreifend gelten

eigene Regeln, die nur dieses Tool betreffen

Konzepte – der Plan für eine Änderung, auch an einem Tool

Anforderungen, Specs und Ähnliches für dieses Tool

Vorgaben für ein Tool: was es können soll und wie es gebaut wird

die tatsächliche Umsetzung

Der Ordner hält, was projektübergreifend ist. Regeln, die für jedes Projekt gelten – Benennung, wie ein Konzept abläuft, wie Ergebnisse gebaut werden –, stehen einmal im Ordner. Ein Repository kann trotzdem eigene Regeln haben und damit eigene Anforderungen, Specs und Ähnliches, wenn sie nur dieses eine Tool betreffen. Ein Konzept, das umgesetzt wird, legt diese Elemente auch im passenden Repository an oder ändert sie und führt das Repository unter results:.

Das Repository hält, was gebaut ist. Der Ordner kann Vorgaben und Regeln für ein Tool und seine Umsetzung machen; im Repository steht die tatsächliche Umsetzung. Sie darf bewusst abweichen – eine Entscheidung beim Bauen – oder einen älteren Stand zeigen, weil der Ordner schon den nächsten Schritt beschreibt. Der Ordner sagt, was gewollt ist, das Repository, was es gibt.
